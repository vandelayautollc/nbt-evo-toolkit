# Keys — what each one does, and which action needs which

This repository ships **no keys**. Every key is either **recovered from your own PSdZData** (your
own BMW-distributed key, for your own car) or **generated by you**. This page is the single map of
them: what each key is, where it comes from, and which action needs it. One tool recovers the
recoverable ones: **`python -m nbtevo.keys`** ([`nbtevo/keys.py`](../nbtevo/keys.py)).

Almost everything is keyed off the **bootloader (BTLD) id** you read from the car
(`capabilities/coding/tools/identify_btld.py`); on this class of head unit that's `00001FFD`.

## The keys

| Key | What it is | Where it lives | Recovered or generated | Secret? |
|---|---|---|---|---|
| **NCD coding key** (Codier-Sign) | per-BTLD RSA (BMWSigVerify, e=3, MD5 on the NBT EVO). Signs the coding dataset so the HU accepts a change | your PSdZData `security/sec_ncdkeys.xml` | recovered — `nbtevo.keys --kind ncd` | **private exponent secret**; modulus is public (baked in firmware) |
| **L3 SecurityAccess key** | per-BTLD RSA BMWSigVerify (e=3). Signs the SecurityAccess *seed* to unlock a **write session** | your PSdZData `security/sec_auth_l3.xml` (E-SYS-wrapped) | recovered — `nbtevo.keys --kind l3` | **private exponent secret** |
| **blobB / owner FSC key** | an RSA e=3 keypair **you generate**. Its modulus replaces the FSC verify modulus (blobB); its private key signs your FSCs | you make it — `fsc/tools/fsc.py keygen` | **generated** (not a BMW key) | **private key secret** (your root of trust for FSCs) |
| *(intermediate)* **E-SYS key + session key** | the PKCS#12 E-SYS private key + a wrapped session key — used only to *decrypt* the two recovered keys above | `security/sec_security.lic` (an XML-wrapped PKCS#12) + `security/sec_keyreference.xml` | part of your PSdZData; its keystore password is **derived** from your own PSdZ resources, not typed (see below) | yes — never commit; never embedded here |

Not keys, but often confused with them: the **SWE flash signature** (RSA-1024/MD5 over a flash
container — verifies *what is flashed*, handled by the flash path) and the **KISS persistence cert
chain** (ROOT→SIGS→FSCS, the certificate-based FSC transport). Neither is something you hold or
recover for the actions below.

## Which key does which action need

| Action | Capability | Key(s) needed | How |
|---|---|---|---|
| Read coding / DTCs / SVK / VIN | coding | **none** (default session) | just transport |
| **Re-sign** an edited NCD (durable coding) | coding | **NCD key** | `nbtevo.keys --kind ncd` → `sign_ncd.py --key` |
| **Write** coding to the car (`27 01/02`) | coding | **L3 key** (+ the signed NCD above) | `nbtevo.keys --kind l3` → `write_coding.py` SA step |
| **Flash** a patch / OPT_DEBUG / blobB (`27 11/12`) | flash_and_patching | **L3 key** | `nbtevo.keys --kind l3` → the SA step in the flash runbook |
| Read / parse an FSC | fsc | **none** (modulus only, to verify) | `fsc.py verify/parse` |
| **Mint** an FSC the HU accepts | fsc | **blobB key (yours)** | `fsc.py keygen` → `fsc.py mint` |
| Install your blobB (so your FSCs verify) | fsc → flash | **L3 key** (to flash the blobB patch) | build the patch (`patch.py`), then flash (L3) |
| **Apply** an FSC to the car (`requestStoreFSC`) | fsc | **L3 key** for the write session; the FSC's own signature authorizes it | the apply runbook |
| Build / run your own QNX binary | qnx_dev / plugins | **none** (file install over SSH) | `scp` + run |

The pattern: **reads need no key; local signing needs the relevant signing key (NCD, or your blobB
key); any write session to the car needs the L3 key.** The L3 key is the one shared across coding
write, flashing, and FSC apply — recovered once, used everywhere.

## Turning a seed into a SecurityAccess key (the L3 handshake)

Every write session unlocks with the **same** seed→key construction, whether it's coding
(`27 01`/`27 02`) or flash (`27 11`/`27 12`). It is **not** "sign the seed" — the seed is folded into
a block that is MD5'd and signed, with a specific wire encoding. Implement it with your own recovered
L3 key (the shared signer is [`nbtevo/l3.py`](../nbtevo/l3.py), `l3_key.json` from `nbtevo.keys --kind l3`):

```
requestSeed  27 01        (coding, level 01)   →  67 01 <seed:8>
             27 11        (flash,  level 11)   →  67 11 <seed:8>

block   = UserID(4 BE) || Controller(4 BE) || seed(8)
          UserID     = the 4-byte testerId sent with requestSeed (00000000 — the value the proven flash used)
          Controller = your BTLD id, e.g. 00 00 1F FD
digest  = MD5(block)                         # 16 bytes
m       = int(digest, little-endian)         # zero-extended to 128 bytes
s       = pow(m, d, N)                        # YOUR L3 key (n=N, d), exponent e = 3
sig     = s.to_bytes(128, "little")          # 128-byte little-endian

sendKey 27 02 / 27 12  <KEY>
          KEY = 00 00 00 20            # word count = 32, big-endian (NOT the raw 128 bytes)
              || sig with each 32-bit word byte-reversed    # 128 bytes
          → total sendKey PDU = 2 + 4 + 128 = 134 bytes
positive = 67 02 / 67 12
```

- **Self-check before sending:** `pow(s, 3, N) == m`, and `m` uses exactly its top 4 32-bit words —
  refuse to transmit otherwise. This is what `nbtevo.l3` does.
- **NRCs:** `0x13` = wire-format/length wrong (the `00 00 00 20` prefix or the word-swap is missing —
  *not* a crypto failure); `0x35` = signature rejected (wrong key/construction); `0x36` = locked out,
  wait the `0x37`-reported delay. A raw `27 12` + 128 bytes (no prefix, no swap) returns `0x13`
  (live-confirmed).
- **Confidence:** the whole handshake is **proven on-car** — the OPT_DEBUG file-copy flash
  authenticated with `testerId 00000000` / `Controller = 00001FFD` and committed (the dev/SSH surface
  it enabled came up afterwards). The e=3 / MD5-little-endian math and the `00000020` + per-word-swap
  wire format are firmware-verified and live-confirmed. If you ever see `0x35` with a known-good key,
  the testerId and Controller are the knobs to vary — but on this unit the proven values above hold.
  The on-car `67` is the proof your key + construction are right.

## Recovering a key (the one tool)

```bash
pip install -e '.[crypto]'
export NBTEVO_PSDZDATA=/path/to/your/psdzdata
export NBTEVO_PSDZ_RESOURCE_JAR=/path/to/your/PSdZ/bin/psdz/resource.jar

python -m nbtevo.keys --btld 00001FFD --kind ncd -o ~/.nbtevo/ncd_key.json   # coding signing
python -m nbtevo.keys --btld 00001FFD --kind l3  -o ~/.nbtevo/l3_key.json    # write/flash unlock
```

Both run the same chain: open the E-SYS keystore in `sec_security.lic`, RSA-unwrap the session key
named by that key file's `encKeyRef` from `sec_keyreference.xml`, AES-128-CBC decrypt the BTLD's
entry in the `sec_*.xml` → a PKCS#8 RSA private key. The modulus printed is public; the private
exponent is written only to the local, `0600`, gitignored key file.

**There is no passphrase to type.** `sec_security.lic` is an XML-wrapped PKCS#12 whose keystore
password PSdZ *derives* — and so does this tool — as `HEX_UPPER(SHA1(passphrase[pid]))`, where `pid`
is read from your own `.lic` and `passphrase[pid]` is decoded from the BMW logo PNGs
(`bmw_logo.png` + `bmw_mini_logo.png`) that ship in your PSdZ runtime's `resource.jar` (reproducing
`com.bmw.psdz.security.img.ResourceParser` + `LicenseValidatorCrypto.genHashedPIN`; see
[`nbtevo/psdz_passphrase.py`](../nbtevo/psdz_passphrase.py)). Point `--resource-jar` at your own
`PSdZ/bin/psdz/resource.jar`, or pass `--bmw-logo`/`--bmw-mini-logo` if you have the PNGs loose.
The toolkit ships none of this — not the logos, not the passphrase, not the derived password; all
come from your own licensed install at run time.

## Proving a recovered key is correct (before you trust it)

- **NCD key** — proven offline, byte-for-byte: `capabilities/coding/validate/selftest.py` recovers
  the key, re-signs your car's own backup NCD, and checks it reproduces the car's existing signature
  exactly. If that passes, the key is right.
- **L3 key** — the acceptance test is on the car: a `27` requestSeed → sign the seed with the L3 key
  → `27` sendKey that returns a positive `67` means the key is correct. The recovery follows the same
  proven method as the NCD key (both are E-SYS-wrapped entries in the same PSdZData security store);
  confirm it with that `67` before relying on it for a write.

## Safety

- The `.gitignore` keeps `*key*.json`, `*.caf`, `*.ncd`, and `sec_*.xml` out of git. Treat every
  recovered private exponent and your blobB private key as secrets — they are the authority to
  change your car; keep them local.
- These are **your** keys for **your** car. A key bound to one BTLD/VIN does nothing for another
  vehicle, and nothing here lets you forge a key you don't already hold or generate. See
  [LEGAL.md](../LEGAL.md).
